# Data Sanity Framework

This module provides a lightweight, config-driven sanity framework for validating CoRE Stack layer outputs. It supports two validation surfaces:

- Vector layers such as GeoJSON, Shapefile, or any format readable by `geopandas`.
- Stats-generator Excel workbooks where each sheet represents an exported layer summary.

The main goal is to catch obvious data quality issues before a layer or workbook is shared further: missing identifiers, missing expected schema fields, invalid data types, negative area/count values, out-of-range percentages, and invalid categorical values.

## Why This Exists

CoRE Stack produces many layers across hydrology, land use, terrain, climate, groundwater, administrative data, and other domains. The generated outputs are consumed in different forms:

- Raw/vector layer outputs from computing pipelines.
- Excel summaries generated by the `stats_generator` app.
- Derived reports and dashboards.

The same conceptual layer can have different column names in vector and Excel form. For example, a vector layer may use compact STAC/source columns, while the Excel export may use longer human-readable names with units. This framework keeps the validation logic centralized while allowing each rule to say whether it applies to `vector`, `excel`, or both.

## Directory Layout

```text
computing/sanity/
  configs/                  # YAML rule configs, one per layer or workbook sheet
  run_validation.py          # Entry points for vector, single-sheet Excel, and full workbook validation
  validator.py               # Builds and runs configured rules
  rules.py                   # Rule implementations
  report.py                  # Converts detailed rule output into a compact report
  rules_review.xlsx          # Exported rule inventory for manual review
```

## High-Level Flow

1. The caller chooses a layer config by config filename, `layer_name`, or Excel `sheet_names`.
2. `run_validation.py` loads the YAML config from `configs/`.
3. The runner reads input data:
   - `geopandas.read_file(...)` for vector layers.
   - `pandas.read_excel(...)` for Excel sheets.
4. The runner passes a validation context:
   - `vector` for vector validation.
   - `excel` for Excel validation.
5. `VectorValidator` builds only the rules whose `applies_to` includes the current context.
6. Each rule validates matching fields and returns field-level results.
7. `report.summarize(...)` returns a compact report:

```python
{
    "status": "PASSED" or "FAILED",
    "errors": [
        {
            "rule": "rule_name",
            "field": "field_name",
            "invalid_count": 10,
            "invalid_uids": ["..."],
            "message": "optional detail",
        }
    ],
}
```

## Validation Contexts

Each YAML rule can include `applies_to`:

```yaml
applies_to: [excel]
applies_to: [vector]
applies_to: [excel, vector]
```

This matters because vector and Excel outputs often use different schemas. During Excel validation, vector-only rules are skipped. During vector validation, Excel-only rules are skipped.

If a config has no rules for the requested context, validation fails with a clear `context_rules_present` error instead of silently passing.

## YAML Config Structure

Each config describes one logical layer or workbook sheet.

```yaml
layer_name: cropping_intensity
sheet_names:
  - croppingIntensity_annual

rules:
  - name: ci_uid_not_null
    applies_to: [excel, vector]
    type: not_null
    field_pattern: "*uid*"

  - name: ci_excel_intensity_max
    applies_to: [excel]
    type: max_value
    field_pattern: "cropping_intensity_unit_less_*"
    value: 3
    allow_missing_fields: true
```

Important fields:

- `layer_name`: Canonical layer name.
- `sheet_names`: Excel sheet aliases that should use this config.
- `rules`: List of validation rules.
- `name`: Unique readable rule name.
- `applies_to`: Context where the rule should run.
- `type`: Rule implementation name from `RULE_MAP`.
- `field`: Exact field name.
- `field_pattern`: Wildcard pattern for matching multiple columns.
- `fields`: Explicit list of fields.
- `exclude_field_patterns`: Patterns removed from field matches.
- `value`: Rule-specific threshold or allowed values.
- `expected_type`: Expected type for `data_type`.
- `allow_missing_fields`: Allows optional field families to be absent.

## Supported Rules

The current rule types live in `rules.py`.

| Rule type | Purpose |
|---|---|
| `not_null` | Fails rows where matched fields are null |
| `data_type` | Checks pandas dtype family: `integer`, `float`, `numeric`, `string`, `boolean` |
| `min_value` | Fails numeric values below `value` |
| `max_value` | Fails numeric values above `value` |
| `allowed_values` | Fails non-null values outside the configured allowed list |
| `required_fields` | Fails when explicit fields are missing |
| `required_any_field_pattern` | Fails when no configured wildcard pattern matches any column |

## Running Validation

Run these commands from the repository root.

Validate a vector layer:

```powershell
python -m computing.sanity.run_validation path\to\layer.geojson --rule cropping_intensity --vector
```

Validate one Excel sheet using the config's sheet aliases:

```powershell
python -m computing.sanity.run_validation path\to\workbook.xlsx --rule cropping_intensity
```

Validate one explicit Excel sheet:

```powershell
python -m computing.sanity.run_validation path\to\workbook.xlsx --rule cropping_intensity --sheet croppingIntensity_annual
```

Validate every sheet in a stats-generator workbook:

```powershell
python -m computing.sanity.run_validation path\to\workbook.xlsx --workbook
```

The code also exposes importable functions:

```python
from computing.sanity.run_validation import (
    run_layer_validation,
    run_excel_validation,
    run_excel_workbook_validation,
)

vector_report = run_layer_validation("data/layer.geojson", "cropping_intensity")
sheet_report = run_excel_validation("data/output.xlsx", "cropping_intensity")
workbook_report = run_excel_workbook_validation("data/output.xlsx")
```

## How Configs Were Created

The configs are based on:

- STAC layer metadata, especially `table:columns`, for vector schemas.
- Stats-generator Excel workbook headers for Excel schemas.
- Domain sanity expectations such as:
  - Areas and counts should generally be non-negative.
  - Percent columns should usually be between `0` and `100`.
  - Cropping intensity should be within `0` to `3`.
  - Identifier columns should not be null.

The STAC catalog root used for metadata discovery:

```text
https://spatio-temporal-asset-catalog.s3.ap-south-1.amazonaws.com/CorestackCatalogs_merged_collection/catalog.json
```

## Adding a New Layer

1. Create a new YAML file under `computing/sanity/configs/`.
2. Add `layer_name`.
3. Add `sheet_names` if the layer appears in Excel exports.
4. Add common identifier/schema rules.
5. Add vector-specific rules from STAC `table:columns`.
6. Add Excel-specific rules from the stats-generator sheet headers.
7. Use `applies_to` on every rule.
8. Run vector and Excel validation separately.
9. Update `rules_review.xlsx` if the rule inventory needs to be shared.

## Reviewing Rules

`rules_review.xlsx` exports the YAML rule inventory into a tabular form for manual review. It includes config name, layer name, sheet names, source comments, rule names, contexts, fields, patterns, expected types, thresholds, and missing-field behavior.

This file is useful when reviewing coverage with non-code stakeholders because it avoids opening many YAML files one by one.

## Current Design Choices

- The framework is intentionally simple: YAML configs plus small reusable rule classes.
- No layer-specific Python classes are required.
- Context-specific behavior is controlled in YAML through `applies_to`.
- The same validator runs for both Excel and vector inputs.
- Configs can be resolved by YAML filename, `layer_name`, or Excel `sheet_names`.

## Known Notes

- Some workbook sheets are derived summaries rather than direct one-to-one vector schemas. For those, Excel rules validate the exported summary columns instead of raw STAC columns.
- `allow_missing_fields: true` is used for optional field families or version-dependent year ranges.
- Full workbook validation uses domain configs when a sheet alias matches. Sheets without a matching config receive a generic fallback check for ID and numeric columns.
